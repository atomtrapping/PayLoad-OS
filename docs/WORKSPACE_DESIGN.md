# Workspace design: one terminal, shared instruments

NotationsOS is the firm's internal workspace for preparing its data products. This document records the shared design language and interaction patterns, the surfaces built on them, and the truths the design must preserve. The dated verification receipts describe the version tested at that time, not a guarantee about subsequent changes.

## The design language

Shared tokens live in `src/app/globals.css`. Existing specialist views also contain local sizing; this iteration does not claim to have migrated every page-local style.

- **Type.** A seven-step rem scale, 12–24 px at the default root size, with a 16 px body. Shared controls and section labels use 14 px; metadata uses 12–13 px. Monospace identifies values, digests, timestamps and instrument labels; explanations remain proportional text.
- **Space and surfaces.** Blue-black opaque surfaces, fine evidence frames and corner registration marks. Broad, desaturated cyan section bands and curved outer ends belong to navigation; evidence panels remain square. A faint unscaled grid is decorative, never a coordinate system. Desktop chrome uses an 80 px minimum header and a 232 px rail; below 768 px the header becomes three rows with a 9 rem minimum, and below 1024 px navigation becomes a horizontal strip.
- **Colour.** Existing semantic status and epistemic hues are unchanged. Gold marks selection and primary action. The separate `--chrome-*` tokens group navigation and frame inspectors; they do not assert observation, verification or runtime health. Text has four roles: heading, primary, secondary, muted. Static contrast tests cover all four on the six opaque grounds, semantic label colours, and the selected palette row; these are not a rendered accessibility audit.
- **Registers.** A ledger table is `.register`: a horizontal scroll region that shows which edge has more table past it, in four background layers and no script, so a column beyond the right edge is never a column nobody knows is there. Identifiers, timestamps and versions do not break mid-token inside one — a release id split across four lines cannot be compared down a column — and a header may take `.th-wrap` where its words are wider than its values. Side padding is 8px: six columns spend twelve gutters.
- **Controls.** `.btn` with `-sm`, `-primary`, `-quiet`; rows that can be selected carry `.row-selectable` with `aria-pressed`, `aria-selected` or `data-selected`; keyboard hints are `.kbd`; first use is `.empty-state`. Product links read their selected state from supported route/query contracts, not a hardcoded Caravan selection. Section headers can wrap their actions instead of squeezing their title.
- **Motion.** `--motion-fast` (120 ms) for controls, `--motion-base` (180 ms, ease-out) for a panel entering, `--motion-slow` (260 ms) for a one-off flash. Nothing animates while the system waits: progress is named in the status line, not spun. `prefers-reduced-motion` disables all of it.

## The shell

`src/components/shell/AppShell.tsx`: a skip link, the sticky top bar (brand, area / page, page search and product links), then the body: one primary navigation and the main surface. Navigation is data (`nav.ts`): Products, Acquisition, Corpus, Notations, Inquiry and Coordination. Numbered section bands and their total are derived from that registry, so another area does not require another navigation implementation. The rail names all three product lines and explains the fixture/local-rail boundary. The home link targets `/`, allowing the root console to accompany these changes without hardwiring another landing page.

The horizontal list owns scrolling on narrow screens; the containing sidebar owns vertical scrolling on desktop. Navigation and arrow-key focus reveal the destination in that actual owner. Product links scope Releases and Retractions only; a product query on Earth or another unscoped instrument does not light a misleading selection.

**The atlas** (`WorkspaceAtlas.tsx`, on the console) is that same registry as a figure, because the rail is a good list and a poor map: it answers where to go next and not what is here. One cell per destination and every cell the same size, so an area's block is exactly as large as the number of places it holds and the figure's ragged edge is the shape of this system rather than a composition; reading order is registry order, so a cell's number is its position in the order `Alt` with an arrow steps through. Band heads take the cyan chrome and the curved outer end the navigation language reserves for navigation, and carry the area's activity line, which the rail has nowhere to show. Nothing else is encoded: `ATLAS_LOSS` states on the surface that size is a count and not an importance, that adjacency is an order and not a workflow, and that the figure reads no store, no rail and no clock — so no cell reports whether its destination is reachable, holds data or is working. It is one tab stop like the rail, with the arrows moving along a band and between bands. Derived from `nav.ts`, so an eighth area appears in the drawing without a line of drawing code. Full account in [UX architecture](UX_ARCHITECTURE.md) under "Knowing what is there".

## The local rails were refusing every request (2026-09-08)

Verifying the notation workspace's new link against the real Rust kernel found something larger than the link. Every browser test in that suite failed at the first fetch, and so would every operator's: `requireLocalRequest` refused a request carrying any of eight forwarding headers, and **Next writes four of them onto every request it hands a route handler**, synthesised from the socket when the client did not send them. Measured on this server rather than supposed: a bare `curl http://127.0.0.1:3115/api/state-kernel`, with no proxy anywhere near it, arrives carrying `x-forwarded-for`, `x-forwarded-host`, `x-forwarded-port` and `x-forwarded-proto`. The notation kernel, the coordination board and the production inspector each refused their own browser.

The reasoning was right about proxies and wrong about this server, so the values are checked rather than the presence: a direct arrival's forwarded host is this host, its port is this port, its scheme is http and its peer is a loopback address. A reverse proxy's are none of those — the public host, usually https, the real client's address — so the deployment the guard exists to refuse is still refused, header by header, each named in the refusal. `forwarded`, `via`, `x-real-ip` and `x-cluster-client-ip` are still absolute: this server never writes one.

What this does not establish is unchanged and still stated: a caller who writes consistent loopback values into all four is not distinguished from a direct arrival, because nothing a handler can read proves how a request reached the socket. What keeps these rails local is the operator's — off by default, bound to loopback. The rails' own wrappers also stopped flattening the guard's finding into a bare `LOCAL_ONLY`; the code keeps its contract and the message now carries what was actually found, because a 403 saying only "same loopback origin" when the answer was "a proxy header named somewhere else" sends an operator to look in the wrong place.

**Verified.** The twelve real-kernel browser tests pass where all twelve failed; the four real-worker production tests pass. Eleven new guard cases: the headers this server writes admitted, each of a reverse proxy's four refused on its own, an appended forwarding list refused whether loopback leads or trails it, the loopback addresses a socket actually reports admitted, the forwarded host read against *this* host rather than a constant, and the four headers Next never writes refused whatever they say.

## The interaction pattern

Every working surface is `.workspace`: a centre surface in two parts (`.workspace-top`, `.workspace-bottom`) and, when an object is selected, a contextual `.inspector` (`src/components/primitives/Inspector.tsx`). From 1024 px the inspector is a sticky column beside the surface, spanning both parts; below that it is an inline detail view directly beneath the top part, so whatever the top part is (a register, a table) stays in reach above it and the forms beneath it stay reachable.

A surface whose centre is a wide register adds `.workspace-register` and keeps that inline view until 1440 px, which is measured rather than chosen: beside the inspector the register gets the viewport less the 232 px rail, the 400 px inspector and the page's padding — 760 px at 1440, which is exactly the release register, and 600 px at 1280, where a sixth of the table sits past its own right edge. A list of titles survives the narrower column and keeps the earlier breakpoint; a register does not. Nothing is modal. The inspector's heading takes focus on narrow screens when the object that opened it may be far away (`focusOnNarrow`), Escape closes it outside text fields, and closing returns focus to what opened it.

Selection connects views: a row pressed in a list, a button pressed on a card, a link followed from inside the inspector all set the same selection; the list marks the selected row and the inspector shows the object in context, with the actions allowed on it and a way to what it refers to.

**A selection is a link** (`src/lib/hashSelection.ts`, `useLinkedSelection.ts`). An inspector that opens on a row and cannot be sent to anyone is half an inspector: the reader can see the thing and cannot say which thing they saw. Spatial Inquiry settled the shape — `#space=S-3`, read on load, written on every choice — and it is one codec now, so a reader learns the encoding once and the surfaces do not each invent one. The hash rather than the query, because writing a hash re-runs no server component: moving down a register costs nothing, and the server render never depends on which row a particular reader had open. Replaced rather than pushed, because six selections would otherwise be six entries in the back button and Back would stop meaning the page before this one. Both directions refuse a name the surface does not hold — an inspector opened on an id the bundle has never seen is a worse answer than the overview — and nothing is written until the surface's data has arrived, so a link is never erased by the page it was opened on still loading. On the case workspace the kind is the key (`#claim=`, `#evidence=`, `#invariant=`, `#ruling=`), so exactly one thing is selected by construction; on the notation workspace `#notation=` and `#relation=` are read together, and a link beats the selection this tab's drafts remembered, because it is the more explicit instruction.

## Slice one: notations (`/notations`)

**Getting between the twenty-six destinations.** The rail is one tab stop rather than twenty-six: a roving tabindex leaves exactly one link tabbable — the page you are on — so Tab enters the rail and Tab leaves it, and the arrow keys do the moving on both axes, because the same list is a column at 1024 px and a strip below it. `Alt`+←/→ steps through the rail order from anywhere; `⌘K` (or the **Jump to…** button, which is the only route on a touch screen) searches the same list and no other. The current tab is scrolled into the rail's own frame on arrival and after every navigation — measured before the change, a 412 px viewport put it 2113 px off-screen in a 2336 px strip that never scrolled. Measured after: 6 tab stops before the page content, down from 32. Full account in [UX architecture](UX_ARCHITECTURE.md) under "Getting between them".

Documented in [Notation workspace](NOTATION_WORKSPACE.md) under "Layout, selection and keyboard". In short: the register with each notation's identity, relation count and standing; the selected notation's inspector with its editor, its origin (created or changed in this draft and not saved, or in saved version N), its relations with direction, the pending commands that name it, and its evidence line; a relation's own inspector; keyboard undo, redo and save through the kernel; named progress. The draft lives in a root provider for the life of the browser document and in the tab's `sessionStorage` for a reload; the rail marks the Notations link `draft` while unsaved work exists, on every page, so no navigation is interrupted and nothing is lost.

## Slice two: candidate production (`/candidates`)

The rail is shown as a process, read only from what it recorded:

- **Four stages**, collection, extraction, normalization, candidate readiness (`processStages` in `src/domain/production.ts`). Every metric carries the field of the demonstration it is read from (`data-source`, shown on hover) and every instant its clock (capture time as declared, record time, decision time, run time, knowledge time, knowledge cutoff, build time). Extraction and normalization are one recorded run on this rail; the stage says so instead of inventing a step.
- **Where coverage stops** (`coverageGaps`): INGEST-only registrations, quarantines and refused steps, each with what stopped, the remediation someone could take, and the field it is read from. The rail takes none of the remediations; the screen performs none.
- **The inspector** on any acquisition, normalization run, build or refusal: provenance as a sequence (`acquisitionSequence`, `normalizationSequence`, `buildSequence`) with each step's identity, exact digest, time and clock, done or refused; for a candidate, evidence beside record: the captured bytes' identity and digest against the candidate's, then field by field the value in the source and the value in the record with what the adapter did between them (`fieldMapping`: copied, trimmed, or missing and not inferred). The source bytes themselves appear only when a committed file has exactly the evidence's content digest (`readCommittedSources` in the adapter, matched on the server); otherwise an explicit unavailable state names the storage key this screen does not open. Nothing on this rail is authored, and the inspector says so.

## Slice six: the release register (`/releases`)

The first of the four surfaces this document listed as keeping their earlier layouts. The register carried nine columns: the coverage sentence, the build identity, the methodology, the digest and the supersession pointer sat in the same row as the counts. Two things followed, both measured on the rendered page rather than supposed. Every row was six lines tall, because one cell held a paragraph while the rest held a word. And the row would not fit — the supersession column sat past the right edge of a 1440 px viewport, inside a scroll region a reader has no reason to suspect, so the one field naming the release that replaced this one was the field nobody saw.

Six columns now, all of them visible at once: the release, its standing, its knowledge cutoff, what it holds, and whether it is certified — what a reader compares down a column. Everything about *one* release moved to the inspector beside it. The supersession chain is the argument for the change: a corrections history is a chain, a table cell can print one link of it, and in the inspector each end is a button that selects that release, so the chain is walked rather than read and looked up. Both ends say what they are when there is nothing there — the first release of the corpus, or one nothing has replaced — rather than showing an empty row. A selection is a link (`#release=…`), the arrow keys move through the register as they do on every other one, and a release the page does not hold selects nothing and is not left in the address bar claiming it does.

Nothing here computes: counts, certification, digests and the chain are the corpus's own fields, counted on the server and passed through.

## Slice five: Spatial Inquiry (`/spatial`)

The linked plan/graph experience over the local spatial analysis service (contract: [Spatial Inquiry v1](spatial/inquiry-v1.md), `src/spatial/*`): how does opening or closing one explicitly declared passage change access through one floor? `src/domain/spatial.ts` reads the service's `payload.spatial-analysis-projection.v1` fail-closed (schema, `LOCAL_ANALYSIS`, the honest flags, a result shaped over the layout's own spaces) and turns it into drawing and reading: validated polygons flipped for the screen, passages between space centres, a graph in possible-depth columns with disconnected spaces last, a depth text in which null is never zero (`unknown` when only possibly reachable, `unreachable` when no graph reaches the space), a mean always shown with its denominator. The graph states its own information loss beside the figure, separately from the analysis's non-claims, because the drawing is a second representation of the same result: columns are depth and rows are an ordering by id, so neither carries distance; every passage at a space attaches at one point on its box; and two spaces at the same depth are joined by a curve bowed clear of the column, because drawn straight that passage would run backwards through the band both boxes occupy and under one of them. It computes no access: every depth, status, neighbour count and mean is the retained result's, and geometry is never used to make a passage.

`src/components/spatial/SpatialInquiry.tsx` is the surface on the shared shell: two saved request ids (defaults are the demonstration's baseline and closed-bridge scenario) inspected over `GET /api/spatial/analyses/{id}`, the comparison asked of `POST /api/spatial/compare` once both are in hand, a baseline/scenario view switch, the plan and the access graph as SVG whose spaces are buttons (`role="button"`, Enter and Space), a table with a button per row, and the inspector: the selected space's status, both depths, distinct neighbours, polygon; every passage naming it with declared and effective state, conditions and provenance, the scenario assumption marked beside the declared fact it never overwrites; the analysis' request, root, method and version, both means with denominators and the sentence that a smaller mean after a closure is not improved access, coverage and unresolved passage ids, scenario provenance; source references by acquisition and evidence digest (retained drawings are referenced, never embedded), layout, result and receipt digests, and the projection's standing flags verbatim. One selection connects plan, graph, table and inspector by space id, and a selection is a link (`#space=<id>`, read on load when it names a space of the layout, otherwise ignored). Without the local service the page says so with the exact remedy and fetches nothing; a service refusal is shown by its code, verbatim, with what it means; a projection outside the contract is refused and nothing is drawn in its place. Labels and provenance render as text, never markup.

**Verified.** `src/domain/spatial.test.ts` (6: contract reading and refusals, depth text, means with denominators and change text, plan geometry and Y flip, graph columns for baseline and closed-bridge, passages of a space and the selection link); `src/components/spatial/SpatialInquiry.test.tsx` (8: disabled service, baseline drawn from the retained example with the comparison asked once, synchronized selection by pointer and keyboard with the link, a linked selection restored and an unknown one ignored, the scenario view with declared facts kept, a refusal shown verbatim with the scenario view disabled and no comparison asked, a projection outside the contract and a disabled server refused, labels as text and other request ids inspected); `tests/e2e/spatial.spec.ts` under the isolated production runner (`npm run e2e:production`), which seeds the runner's evidence root with the retained demonstration and checks the page against the real service: plan, graph and table counts, P-09 unresolved, the means, selection across surfaces and by keyboard, the link, the scenario's closure of P-07, the comparison's three changed spaces, a fresh load of a selection link, no horizontal overflow at desktop and 412 px, no serious or critical axe findings, no page errors, no request leaving the origin. `/spatial` is in the overflow guard.

## What the design does not bend

- Fixtures are identified on the surface (the fixture banner, `FIXTURE` markers), never implied by polish.
- No control is shown for an operation the backend has no contract for: evidence-reference attachment stays disabled with the reason; no remediation is a button.
- A preview is never presented as saved, a candidate never as admitted, a source never as verified: origin lines, `UNADMITTED`, `UNRESOLVED`, `canonical null` and the not-claimed lists are rendered from the records.
- Evidence and interpretation stay apart (the notation evidence panel), evaluation and verification stay apart (source truth and field accuracy are not claimed), refused is not false (refusals are records of their own with the rail's words), valid time and knowledge time are labelled as such.

## Slice five: the observation replay surface (`/compute/observations`)

Described in [Recorded observation replay](RECORDED_OBSERVATION_REPLAY.md). The same shell and inspector pattern over a contract rather than a rail: the frame diagram and the timeline are the centre's two pictures, both drawn from the manifest and the computation and nothing else, and both are selection surfaces; beneath them the observation and comparison registers; beside them the inspector for the selected observation. Distinctions are carried as badges from a closed vocabulary, so a synthetic input, a supplied estimate, an unresolved placement and a residual-only comparison never read as one another. Every state on the surface is the code the computation emitted, and every explanation is the meaning recorded for that code.
